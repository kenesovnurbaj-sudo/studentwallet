# Команда StudentWallet: роли и задачи

## Важное про решение «весь код пишет один человек»

Так можно, и для скорости это даже удобно: единый стиль, нет конфликтов в git. Но есть три риска, о которых надо знать заранее:

1. **Оценка вклада.** В курсе обязательны Git и Agile. Преподаватель может смотреть историю коммитов и Sprint Review. Если коммиты есть только у одного человека, остальным трудно доказать вклад. **Решение:** все четверо остальных тоже коммитят в репозиторий свои файлы (`docs/`, `design/`, `tests/manual/`, `postman/`, `shortcuts/`). Это реальные deliverable курса, а не имитация.
2. **Узкое место.** Если разработчик заболел или не успел, встаёт весь проект. **Решение:** второй человек (QA) каждый спринт запускает проект у себя по README и делает code review пулл-реквестов (читает, комментирует, одобряет). Так он знает код и может подхватить.
3. **Нагрузка.** 68 story points на 7 спринтов, около 10 SP на спринт, и всё кодит один. Это посильно, если остальные не тянут задачи на себя вручную. **Решение:** если на ревью спринта видно, что разработчик не успевает, часть простых задач (например, CSV-экспорт, страница целей) передаётся второму человеку. Договоритесь об этом заранее.

**Рекомендация:** спросите преподавателя, допустим ли формат «один разработчик». Если он требует вклад всех в код, переходите на вариант из конца файла.

## Роли

| # | Роль | Что делает | Что сдаёт (и коммитит в git) |
|---|---|---|---|
| 1 | **Lead Developer** (весь код) | Backend, frontend, интеграция с API для Siri, деплой, исправление багов | `backend/`, `frontend/`, README, Swagger-документация API |
| 2 | **Product Owner / Business Analyst** | Proposal, требования, user stories, приоритеты backlog, критерии приёмки, принимает работу на Sprint Review | `docs/01-proposal.md`, `docs/02-requirements.md`, `docs/03-backlog.md`, руководство пользователя |
| 3 | **Scrum Master / Project Manager** | Доска, Sprint Planning, daily stand-up, Retrospective, burndown, контроль сроков, итоговый отчёт и презентация | `docs/sprints/sprint-N.md` (план, итоги, ретро, burndown), слайды |
| 4 | **UI/UX Designer** | Wireframes и макеты в Figma, цвета и компоненты, проверка удобства, экспорт ассетов и спецификации для разработчика | `design/` (экспорт из Figma, PNG/PDF), `docs/04-ui-ux.md` |
| 5 | **QA Engineer + Siri/Shortcuts** | Тест-план, тест-кейсы, баг-репорты, Postman-коллекция, ревью PR, сборка команд в «Командах» для Siri, сценарий демо | `docs/test-plan.md`, `tests/manual/`, `postman/`, `shortcuts/` (скриншоты и инструкция), `docs/demo-script.md` |

Совет: Product Owner и Scrum Master обязательно присутствуют на каждом Sprint Review. Остальные присутствуют, когда показывают свою часть.

## Задачи на Спринт 1 (регистрация, вход, БД, wireframes)

| Роль | Задачи |
|---|---|
| Lead Developer | Создать репозиторий и ветки (`main`, `develop`), запустить backend-каркас из этого архива, подключить PostgreSQL (по желанию), реализовать экраны регистрации и входа на frontend (React), US-1 и US-2 |
| Product Owner | Дописать и согласовать proposal, перенести 21 user story из `StudentWallet_project_plan.md` на доску, добавить критерии приёмки к US-1 – US-5 |
| Scrum Master | Создать доску (GitHub Projects/Trello), настроить колонки Backlog / Sprint / In progress / Review / Done, провести Sprint Planning, завести таблицу burndown |
| UI/UX Designer | Wireframes: вход, регистрация, список трат, форма «добавить трату», дашборд. Выбрать палитру и шрифт, показать команде |
| QA + Siri | Написать тест-кейсы для регистрации и входа, поднять backend локально по README и проверить через Swagger (`/docs`), начать Postman-коллекцию, изучить, как в «Командах» делать POST-запрос |

## Рабочие правила

- Ветки: `main` (стабильная), `develop` (текущая работа), `feature/us-4-add-expense` (по истории).
- Pull request обязателен, ревьюер: QA. Без одобрения в `develop` не вливаем.
- Сообщения коммитов: `US-4: add expense endpoint`.
- Каждый спринт: тег `sprint-N` на `main`, чтобы можно было показать состояние на конец спринта.
- Daily stand-up: 15 минут, три вопроса (что сделал, что буду делать, что мешает). Можно в чате текстом.

## Вариант Б: если преподаватель требует код от всех

Тогда делим код так, но договоритесь об интерфейсах заранее (формат API описан в Swagger):

| Роль | Кодовая часть |
|---|---|
| Lead Developer | Backend: auth, расходы, бюджеты, деплой |
| QA | Автотесты (pytest), модуль аналитики на backend |
| UI/UX Designer | Верстка (HTML/CSS/React-компоненты) по своим макетам |
| Product Owner | Админ-панель (простые страницы) и экспорт CSV |
| Scrum Master | Страница целей накопления и уведомлений |

Это потребует больше координации и ревью, зато вклад виден у всех.
